    CI/CD Cheat Sheet¶

    Quick-reference tables from 31 lessons of the free CI/CD Mastery Path, in course order from beginner to advanced. Each section links to the full lesson with explanations and runnable examples.

    Level 1 · Pipeline Foundations¶

    01 · What CI/CD Is and Why Pipelines Exist¶

    The three terms

    Term What it means What it needs
    Continuous Integration (CI) Developers merge small changes into a shared mainline frequently, and every change is automatically built and tested A build that runs without human steps, tests worth trusting, a rule that a broken mainline is fixed first
    Continuous Delivery Every change that passes the pipeline is kept in a deployable state and can be released to production at any time with one decision Automated packaging, deployment to staging, repeatable release steps
    Continuous Deployment Every passing change is released to production automatically, with no manual gate High-confidence tests, monitoring, fast rollback, feature flags

    02 · Pipeline Anatomy: Triggers, Jobs, Steps & Stages¶

    The vocabulary, side by side

    Concept Meaning GitHub Actions Jenkins (Declarative) minici
    Pipeline / workflow The whole automated process, defined as code A workflow file in .github/workflows/ A Jenkinsfile A YAML file
    Trigger The event that starts a run on: (push, pull_request, schedule, workflow_dispatch...) SCM polling/webhooks, triggers {}, "Build now" You run the command
    Job A unit of work on one executor, with its own clean workspace jobs.<id> A stage (with its own agent if declared) jobs.<id>
    Step One command or reusable action inside a job steps: (run or uses) steps {} (sh, bat, plugin steps) steps: with run
    Stage A named phase grouping work (build, test, deploy) Not a first-class concept; jobs and needs express it stage('Build') Levels computed from needs
    Runner / agent The machine or container that executes jobs runs-on: agent {} Your laptop
    Dependency Order between jobs needs: Sequential stages; parallel {} blocks needs:
    Condition Whether something runs if: when {} if:
    Artifact Files produced for later use or download upload/download artifact actions archiveArtifacts artifacts:
    Cache Reusable files to speed up later runs cache action plugins or agent-local caches cache:
    Environment / secrets Variables, protected targets env, secrets, environment: environment {}, credentials binding env:

    03 · GitHub Actions Essentials¶

    Documented limits worth knowing (GitHub "Actions limits" page, October 2026)

    Limit Value
    Job execution time, GitHub-hosted runners 6 hours (the job is terminated)
    Job execution time, self-hosted runners 5 days
    Jobs generated by one matrix 256 per workflow run
    Workflow run time (including waiting and approvals) 35 days
    Time a run can wait for an environment approval 30 days
    Re-runs of one workflow run 50
    Cache storage per repository 10 GB
    Concurrent jobs (standard hosted runners) Depends on plan: 20 (Free), 40 (Pro), 60 (Team), 500 (Enterprise)

    04 · Jenkins Essentials and the Jenkinsfile¶

    Jenkins vs GitHub Actions in one table

    Jenkins GitHub Actions
    Hosting You run controller and agents GitHub runs the orchestrator; hosted or self-hosted runners
    Pipeline file Jenkinsfile (Groovy DSL) YAML in .github/workflows
    Extensibility Plugins (installed on the controller) Marketplace actions (executed per job)
    Isolation Depends on how you configure agents; shared controller Fresh VM per job on hosted runners
    Maintenance burden Upgrades, plugin updates, backups, scaling Mostly the workflows themselves
    Strengths Full control, on-prem, custom hardware, mature, flexible Tight GitHub integration, low setup, ecosystem
    Typical weakness Plugin sprawl, snowflake controllers Locked to GitHub, usage limits

    05 · Testing Gates and Fast Feedback¶

    The test pyramid, applied to pipelines

    Layer Speed Scope Typical count Where in the pipeline
    Static checks (format, lint, types) seconds Code style and obvious mistakes n/a First
    Unit tests seconds to a minute One function or class, no network Hundreds to thousands First/second
    Integration tests minutes Several components, a real database or service Tens to hundreds After unit tests
    End-to-end / UI tests many minutes The whole system through its interface Few, on critical paths Late, often only on main or staging
    Non-functional (performance, security scans) minutes to hours Specific qualities Targeted Parallel, or scheduled

    06 · Reproducible Builds and Caching¶

    What makes a build reproducible

    Input How to pin it
    Source code The exact commit SHA (CI checks out the triggering commit)
    Dependencies Lockfiles (package-lock.json, poetry.lock, go.sum, Cargo.lock) with exact versions and hashes; install with the lockfile (npm ci, pip install --require-hashes), not a fresh resolution
    Toolchain A pinned version of the compiler/runtime (setup-python with an exact version, a container image digest)
    Base images image@sha256:... digests, not :latest
    Build environment A clean workspace and container; no reliance on what a previous build left behind
    Time and randomness Don't embed timestamps or random IDs in artifacts (or set SOURCE_DATE_EPOCH)
    Network Fetching "latest" at build time makes the build a function of the internet

    07 · Artifacts, Registries and Versioning¶

    Where artifacts live

    Kind Examples Notes
    Pipeline artifact storage GitHub upload/download artifact actions; Jenkins archiveArtifacts Short-lived outputs for passing files between jobs or downloading; retention is configurable and storage-limited by plan
    Language package registries PyPI, npm, Maven Central, crates.io; private mirrors (Artifactory, Nexus, GitHub Packages) Versioned packages for libraries
    Container registries Docker Hub, GHCR, ECR, GCR, ACR, Harbor Images addressed by tag and digest
    Generic object storage S3/GCS buckets with checksums Binaries, installers, release bundles

    08 · Secrets in Pipelines¶

    Supplying secrets properly

    Platform Mechanism Notes (from documentation; not run)
    GitHub Actions Repository, environment and organization secrets, referenced as ${{ secrets.NAME }} Masked in logs when printed verbatim; not passed to workflows from forked pull requests by default; environment secrets can require approval
    Jenkins Credentials store with withCredentials/credentials() bindings Masked in console output; scope credentials by folder/domain; a build on the controller can reach more than it should
    Cloud-native A secrets manager (Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault) read at deploy/run time Rotation, audit, fine-grained access

    09 · Branching Strategies and Pull Request Checks¶

    Strategies compared

    Strategy Shape Integration frequency Fits
    Trunk-based development Everyone commits to main (or merges very short-lived branches, under about a day or two) behind feature flags Continuous Teams practising CI/CD seriously; needs strong tests and flags (Level 3 · 02)
    GitHub flow Short-lived feature branches, pull request, review, merge to main, deploy from main Daily to weekly Most web/SaaS teams
    GitFlow develop, feature/*, release/*, hotfix/*, main Per release Software shipped in discrete versions with long support windows; heavy for continuous delivery
    Release branches off trunk Trunk plus release-1.4 branches receiving only fixes Continuous on trunk Products with several supported versions

    06 · Quality Gates: Coverage, Lint & Analysis¶

    The other gates

    Gate Catches Typical false-positive source
    Formatter check (black --check, gofmt -l) Style drift None if the formatter is deterministic; fix with auto-format
    Linter (ruff, eslint) Unused names, likely bugs Rules that do not fit your code; tune rather than disable everything
    Type checker (mypy, tsc) Interface mismatches Third-party libraries without types
    SAST (static security analysis) Injection, unsafe functions High noise; triage and baseline
    Dependency scan Known-vulnerable versions Vulnerabilities in code paths you never call
    Secret scan (Level 1 · 08) Committed credentials Test fixtures that look like keys
    License check Incompatible licenses Ambiguous metadata
    Performance budget Slower endpoints, bigger bundles Noisy shared runners

    08 · Runners & Agents: Where Your Jobs Actually Run¶

    Hosted vs self-hosted

    Hosted (provided by the CI vendor) Self-hosted (you run the machine)
    Setup None Install the runner/agent, keep it patched
    Isolation A fresh VM per job, discarded afterwards Whatever you build: VM, container, or bare machine reused
    Hardware Vendor's sizes (larger ones cost more) Anything: GPUs, ARM, mainframes, private network access
    Cost Per minute (some free allowance) Machines, power, people
    Network Public internet Can reach your private systems
    Max job time 6 hours (hosted, documented) 5 days (self-hosted, documented)

    The mapping and its three categories

    Changed file Affected
    services/api/app/main.py api
    libs/common/util.py api, web (shared library fans out to dependents)
    Makefile api, docs, web (global path)
    .github/workflows/ci.yml api, docs, web
    README.md nothing

    10 · Project — A Workflow Linter¶

    The rules

    Rule Flags Why it matters
    W001 No permissions: at the workflow level (and not every job sets one) The token defaults to the repository setting, which may be read-write
    W002 pull_request_target workflow that checks out the PR head Untrusted code running with a privileged token and secrets
    W003 uses: not pinned to a 40-hex commit SHA (also applies to reusable-workflow calls) Tags and branches can be moved; a SHA cannot
    W004 Job without timeout-minutes A hung job runs until the platform limit (hours)
    W005 Untrusted ${{ github.event... }} inside run: or github-script Script injection
    W006 Deploy-looking job with no concurrency: Two runs can deploy at once; the older may finish last

    Level 3 · Delivery & Release Engineering¶

    01 · Deployment Strategies¶

    The four strategies

    Strategy How Rollback Extra capacity Main risk
    Recreate Stop the old version, start the new one Redeploy the old one None Downtime between stop and start
    Rolling Replace instances a few at a time Roll the other way Small surge (e.g. +1 instance) Old and new versions serve traffic together
    Blue-green Build a full second environment, switch traffic at once Switch back A whole second copy during the cutover Cost; shared database must suit both
    Canary Send a small share of traffic to the new version, widen if healthy Send it back to 0% Small Needs good metrics and enough traffic to read them

    02 · Feature Flags: Decoupling Deploy from Release¶

    Types of flags have different lifetimes

    Type Purpose Lifetime
    Release flag Hide unfinished or risky work Days to weeks, then delete
    Experiment flag A/B test with measurement Until the experiment concludes
    Ops flag / kill switch Disable a feature under load or incident Long-lived by design
    Permission flag Entitlements per customer Long-lived (really a product feature)

    03 · Database Migrations: Expand & Contract¶

    Dangerous operations, and safer shapes

    Operation Why it hurts Safer shape
    Rename column or table Breaks the other version Add new, dual-write, backfill, switch, drop old
    Add NOT NULL column without a default Fails on existing rows; may rewrite the table Add nullable, backfill, then add the constraint (validated)
    Change a column type Rewrites data, breaks readers New column with the new type, migrate, switch
    Add an index on a large table Can block writes Use the engine's online/concurrent index creation where it exists
    Drop a column Irreversible data loss; breaks old code Stop all use first, back up, then drop
    Large UPDATE in one statement Long lock, huge log Batches with pauses

    04 · Rollbacks: Going Back, and When You Cannot¶

    What a rollback can and cannot undo

    Change Rollback restores it?
    Stateless application code Yes: redeploy the previous artifact
    Configuration / feature flag Yes: revert the value (Lesson 02: usually the fastest)
    Additive schema change (new nullable column) Not needed: old code ignores it
    Destructive schema change (drop/rename) No: data is gone or old code breaks
    Data transformed in place (e.g. rounded prices) No, unless you kept the original
    Messages published, jobs enqueued No: consumers already saw them
    External effects (emails, payments, API calls) No
    A new version of a consumed contract (event schema) Only if consumers tolerate both

    07 · Release Management: Versions, Changelogs & Trains¶

    Branching models for releases

    Model Idea Fits
    Trunk-based Everyone integrates to main daily; releases are tags on main; unfinished work is hidden by flags (Lesson 02) Services deployed often
    Release branches Cut release/1.5 from main; only fixes go there; main moves on Products that must support several versions
    Gitflow-style Long-lived develop plus feature, release and hotfix branches Slower, scheduled releases; carries heavy merge overhead

    08 · Supply-Chain Security for Pipelines¶

    Where attacks enter

    Entry point Example Defence
    Direct dependency A maintainer account is taken over and a new version ships malware Pin versions, review updates, use lockfiles with hashes
    Transitive dependency A library of a library is compromised SBOM, scanning, fewer dependencies
    Typosquatting / dependency confusion A public package with the same name as your private one wins resolution Scoped/namespaced registries, explicit index config
    Base image or tool A mutable tag now points to a different image Pin by digest
    CI action or plugin A tag on a third-party action is moved to malicious code Pin to a commit SHA (Lesson 10's rule W003)
    Build system A compromised runner or poisoned cache injects code into your artifact Ephemeral runners, isolated builds, provenance
    Your own pipeline A pull request exploits script injection to steal secrets Hardening (Level 4 · 01)
    Distribution Someone swaps the artifact on the download server or registry Checksums, signatures

    09 · Measuring Delivery: The DORA Metrics¶

    The four measures

    Measure Question Pipeline-level data you need
    Deployment frequency How often do we ship to production? Timestamps of production deploys
    Lead time for changes How long from commit to running in production? Commit time and deploy time per change
    Change failure rate What share of deploys cause a failure needing remediation? A record of which deploys led to incidents, rollbacks or hotfixes
    Time to restore How long to recover when a deploy goes wrong? Failure start and recovery time

    Level 4 · Pipelines at Scale¶

    01 · Threat-Modelling the Pipeline¶

    Step 1: What are you protecting?

    Asset If compromised, an attacker can...
    Deploy credentials / cloud roles Change production directly
    Source repository write access Insert code that every later build trusts
    Signing keys / signing identity Make malicious artifacts look genuine
    Secrets in the CI system Reach databases, registries, third-party APIs
    Build artifacts and caches Ship tampered binaries without touching source
    The runners themselves Pivot into internal networks; persist between jobs
    Pipeline definitions Change what is checked (turn off the gates)
    Logs and reports Leak secrets; hide evidence

    02 · Speed & Cost¶

    Where time actually goes

    Phase Lever
    Waiting for a runner Pool size, autoscaling (see below)
    Checkout Shallow clone (but see Level 2 · 09), sparse checkout for monorepos
    Setup and dependency install Caching with a good key (Level 2 · 02), prebuilt images
    Build Incremental or remote-cached builds, parallel compilation
    Tests Sharding (Level 2 · 01), run only affected tests (Level 2 · 09), fix slow tests
    Packaging, upload, publish Skip on PRs; compress less; upload once
    Fixed overhead per job Fewer, larger jobs vs more parallelism

    04 · GitHub Actions at Scale¶

    Limits shape designs

    Limit (documented) Design consequence
    Hosted job ≤ 6 h Long jobs (full-fleet integration, model training) need self-hosted runners or must be split
    Self-hosted job ≤ 5 days Still not a place for week-long batch work; use a scheduler built for it
    ≤ 256 jobs per matrix Large fan-out needs several workflows or dynamic matrices split in chunks (Level 2 · 01)
    Cache 10 GB per repository, LRU Many large caches evict each other; share keys, cache downloads (Level 2 · 02)
    Concurrent jobs by plan (20/40/60/500) A busy org queues; the cap, not your longest job, sets wall time (Lesson 02)
    Approval wait ≤ 30 days Long-pending production approvals silently expire
    Re-runs ≤ 50 attempts Don't build a "retry until green" habit; fix flakes (Level 2 · 05)
    Log and artifact retention Download evidence you need for audit before it expires, or export it (Lesson 05)

    05 · Audit & Compliance¶

    What an auditor wants to see

    Question Evidence the pipeline should produce
    Was this change reviewed by someone other than its author? Pull-request approvals, with identities and timestamps, enforced by branch protection (not just policy)
    Was it tested and scanned? Required-check results tied to the exact commit
    Who approved the production deployment? Environment approval record (Level 2 · 07), with approver identity
    What exactly was deployed? Version, artifact digest, commit SHA, build ID (Level 3 · 07 traceability)
    Could the same person write, approve and deploy a risky change? Access reviews showing separation of duties
    Were emergency changes handled properly? Break-glass records with after-the-fact review
    Can anyone tamper with the history? Immutable or tamper-evident logs, restricted deletion rights
    Is access reviewed? Periodic access review output for repositories, runners, secrets

    06 · Testing Pipelines¶

    Testing for the failure modes you fear

    Fear Test
    Deploys when tests fail Break a test, assert no deploy (done above)
    Deploys from a pull request or a fork Run with a PR-like event context and assert the deploy job is skipped
    Leaks a secret to logs Run with a sentinel secret value and grep the logs for it (a masking test)
    Runs two deploys at once Trigger two runs and assert serialisation (needs the real platform)
    Passes with an empty test set Make pytest collect zero tests and assert the job fails (exit code 5 in pytest for "no tests collected")
    Succeeds when a step is skipped by mistake Count the steps that actually ran

    07 · Pipeline Incidents¶

    Classes of pipeline incident

    Class Example First priority
    Broken main A merge turns the main branch red; nobody can merge Restore green quickly: revert or fix forward
    Pipeline outage The CI server, runner pool, registry or artifact store is down Restore the ability to ship; know the emergency deploy path
    Bad release shipped A deploy caused customer impact Stop the bleeding: rollback, flag off (Level 3 · 04)
    Secret leak A credential in a repository, a log or an artifact Revoke and rotate first, investigate second
    Compromised build A malicious dependency, action or runner Contain, preserve evidence, rebuild trust
    Cost spike A loop or matrix burns the budget Cancel the runs, cap spend, fix the trigger
    Data-affecting migration A migration locks or corrupts a table Halt, assess, restore (Level 3 · 03)

    09 · Golden Paths: Making the Right Way the Easy Way¶

    Templates vs enforcement

    Approach How updates reach teams Cost
    Copy-once template They don't, unless someone pushes a PR Cheap to build; drift over time
    Template + update bot A bot opens PRs when the template changes Moderate; needs tooling
    Thin caller + reusable workflows Teams reference a versioned workflow; updating the tag updates behaviour (Level 2 · 03) Moderate; coupling and version policy
    Central policy enforcement Org rules require checks regardless of the repo's own files (Lesson 04) Highest; strongest guarantee
